## Behavioral Rules

**Ask, don't guess.**

- Ask clarification questions before implementing when scope, approach or details are uncertain
- Proceed with implementation only when requirements are clear

**NEVER hardcode secrets.**

- No passwords, API keys, tokens or connection strings in code, docs, tests or commit messages
- Secrets come from <SECRETS_SOURCE> only (e.g. `<SECRETS_RUN_COMMAND>`)

**NEVER expose secret values in commands or output.**

- Inject secrets as environment variables and reference them by name (`$SERVICE_TOKEN`), never paste values
- Do not `cat`, `echo` or print env files or secret files

**NEVER force-push.**

- No `git push --force` / `--force-with-lease` on any branch
- If history must be rewritten, stop and ask the user to do the push themselves
- Reach the same goal with a revert commit or by cherry-picking forward

**Comment rationale and connections.**

- Explain *why*, not *what*; note connections to other files (`# Used by <path>`)
- One line when possible

**NEVER hardcode URLs, hosts or ports.**

- All external URLs come from configuration/environment
- Violation check after any change: grep the diff for `localhost`, `127.0.0.1`, hardcoded ports

**DRY — find the real source.**

- Change the actual source of truth, not what merely looks related
- 3+ repetitions = extract a shared helper; one cross-cutting operation = one function
